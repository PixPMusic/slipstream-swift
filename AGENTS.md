# Working on Slipstream

Read [CONTRIBUTING.md](CONTRIBUTING.md) before changing code or opening a PR.
Keep the solution small, native, and focused on one underlying problem.

## Repository map

- `Slipstream/` contains the SwiftUI app, shared core, and resources.
- `Package.swift` exposes the core for `Tests/`; `Packages/` contains SDK wrappers.
- `project.yml` owns project structure. Regenerate with XcodeGen when it changes;
  commit the generated Xcode project and dependency lockfile when affected.
- `scripts/` owns build and distribution commands; `Config/` owns build settings.
- `docs/` describes configuration, CI, distribution, and privacy.

## Implementation and verification

- Inspect the working tree and preserve unrelated changes. Use the intended
  base; ordinary PRs target `main`, while stacks name their parent explicitly.
- Consider Mac, iPhone, and iPad when changing shared UI. Check compact and wide
  layouts, safe areas, orientation, and Duo behavior when relevant. State which
  surfaces were exercised and which remain unchecked.
- For logic, data, or state bugs, reproduce with a focused failing test before
  fixing when practical. Extend existing core tests with synthetic fixtures.
- Purely visual fixes use matched before/after captures as proof; do not add
  tests that only mirror layout or copy. Interaction changes also need a short
  recording when still images cannot show the result.
- Exercise the affected native app. A successful build or desktop browser
  viewport does not establish iOS behavior, and Simulator does not establish
  physical-device playback, AirPlay, or Duo behavior.
- Capture the original behavior before editing. Attach evidence to the PR using
  the [upload workflow](CONTRIBUTING.md#upload-pr-evidence). Local file paths and
  “screenshots retained locally” do not provide evidence to reviewers.
- Report unavailable access and verification gaps honestly. Do not claim an
  untested platform works or fabricate a before capture after applying the fix.

## Data, devices, and cleanup

- Prefer **Try Demo** (Mac: `--demo`) and synthetic content for public evidence.
  If reproducing a bug requires an account, inspect every capture for private
  content before uploading. Never expose cookies, credentials, account details,
  real hostnames, unrelated threads, or Nebius/customer information.
- An authorized signed-in account may be used for playback verification. Preserve
  existing sign-in: do not sign out, reset app data, or remove saved credentials
  unless explicitly requested. Prefer a temporary demo launch when synthetic
  content is sufficient, and sanitize account captures before public uploads.
- Keep evidence, scratch notes, build products, and local signing settings out
  of commits. Do not change bundle IDs or signing to make a PR build locally.
- Use at most one simulator or emulator at a time. Check for sessions used by
  other work; do not stop or take over someone else's device session.
- In T3 Code, use `device_list`, `device_open`, and its returned AgentDevice
  command to operate devices, then `device_screenshot` to inspect them.
- Stop only the processes and device sessions you started, unless asked to
  leave them running. Track your own processes; do not kill by name or pattern.

## Publishing

Use the configured contributor identity. Keep AI authorship, coauthor, and
“generated by” footers out of commits. Disclose the actual full model name and
harness in the PR body as described in CONTRIBUTING.md. Preserve bot-managed
body blocks when editing a PR. Never merge a PR unless explicitly asked.
